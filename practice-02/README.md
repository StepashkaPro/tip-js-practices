## Модель данных и создание задачи
Модель задачи:
{
  id: 20,
  title: "Подготовить демонстрацию",
  completed: false,
  priority: "medium"
}
Правила полей:
Поле     |Правило
id       |Число, положительное безопасное целое: Number.isSafeInteger(id) && id > 0. В пределах списка уникален.
title    |Строка. После trim() длина от 1 до 100 включительно. В объект записывается очищенная строка, внутренние пробелы сохраняются.
completed|Логическое значение. При создании новой задачи всегда false.
priority |Строго одно из значений: "low", "medium", "high". По умолчанию — "medium".


Контракт функции createTask:
export function createTask(id, title, priority = "medium")


Почему уникальность id проверяется в addTask, а не в createTask:
createTask не получает массив задач, поэтому не может проверить уникальность. Это делается в addTask, куда передан весь список. Создание отдельной записи и вставка её в коллекцию — разные операции

## Чтение списка и расчёт сводки

|Функция                |Результат                                | Метод |
|findTaskById(tasks, id)|Первый объект с указанным id или undefine|find   |
|getPendingTasks(tasks) |Новый массив задач с completed === false |filter |

Правила getTaskStats:
total = количество задач
completed = количество задач с completed === true
pending = total - completed
progress = completed / total * 100, если total > 0; иначе 0

Все четыре поля — числа. progress возвращается без округления.

Почему findTaskById возвращает ссылку, а не копию:
метод find не копирует элементы. Это соответствует контракту: функция только
читает. Для изменения предусмотрены отдельные функции задания 6.4.

Почему progress — число, а не строка:
форматирование (знак %, toFixed) — задача вывода. Число переиспользуемо
и удобно для сравнения в проверках.

## Добавление, изменение и удаление

Контракты:
Успех: { ok: true, tasks: <новый массив> }
Ошибка: { ok: false, error: "..." }

|Функция         |Что меняет              |Метод                |
|addTask         |добавляет задачу в конец|spread массива       |
|setTaskCompleted|только completed        |map + spread объекта |
|renameTask      |только title            |map + spread объекта |
|removeTask      |удаляет запись          |filter               |

Требования к иммутабельности:
входной массив и его объекты не изменяются;
успех возвращает новый массив;
изменяемый объект создаётся заново, остальные переиспользуются;
порядок сохраняется;
нет глобального изменяемого списка;
push, splice и прямое присваивание свойств запрещены.

Почему повторная установка статуса — успех:
единообразие контракта; map создаёт новый массив,
{...task, completed} — новый объект выбранной задачи.

Почему одного сравнения ссылок на массив недостаточно:
новый массив может содержать испорченный объект.
Проверять нужно и ссылки, и значения полей.

## 8. Вывод

В ходе работы я освоил функции с возвращаемыми значениями, работу
с массивами объектов, методы `find` / `filter` / `map`, поверхностное
копирование через spread и разделение кода на ES-модули. Ошибки
возвращаются как данные `{ ok: false, error }`, а не выбрасываются.

Наиболее показательной ошибкой оказался пропущенный `return`
в стрелочной функции с блочным телом — функция возвращала `undefined`,
хотя выражение вычислялось. Второй важный момент — поверхностное
копирование: `[...tasks]` не копирует объекты внутри, поэтому при
изменении задачи нужно создавать новый объект через `{ ...task, поле }`.

По сравнению с ПР1 расчёты перешли от переменных к массиву объектов
и чистым функциям. Все девять функций реализованы, проверки пройдены
полностью (35 / 35), оба сценария запускаются одной командой.
